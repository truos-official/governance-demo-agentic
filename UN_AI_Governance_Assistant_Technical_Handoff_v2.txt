5. DOCKERFILE & BUILD RULES
================================================================================

Backend Dockerfile (project root):
  FROM python:3.11-slim
  WORKDIR /app
  RUN apt-get update && apt-get install -y build-essential curl && rm -rf /var/lib/apt/lists/*
  COPY requirements.prod.txt .
  RUN pip install --no-cache-dir -r requirements.prod.txt
  COPY src/ ./src/
  COPY data/ ./data/
  EXPOSE 80
  CMD ["uvicorn", "src.api:app", "--host", "0.0.0.0", "--port", "80"]

CRITICAL BUILD RULES:
  1. ALWAYS --platform linux/amd64
     Azure Container Apps runs on amd64. Building on Mac M1/M2 without this flag
     produces arm64 image that silently fails on Azure.

  2. ALWAYS --no-cache when Python code changed
     Docker layer caching can serve stale src/ files. Use --no-cache to guarantee
     all code changes are included.

  3. INCREMENT version tag
     Current: v5. Next: v6. Never reuse a tag — Azure may not pull a re-pushed tag.

  4. Use requirements.prod.txt for production builds
     requirements.txt includes dev/test tools (pytest, etc.) not needed in container.

Full build + push + deploy sequence:
  docker build --no-cache --platform linux/amd64 \
    -t governancedemoacr.azurecr.io/governance-backend:v6 .
  az acr login --name governancedemoacr
  docker push governancedemoacr.azurecr.io/governance-backend:v6
  az containerapp update \
    --name governance-backend \
    --resource-group rg-governance-demo \
    --image governancedemoacr.azurecr.io/governance-backend:v6

6. REDIS CLIENT — CRITICAL CONFIGURATION
================================================================================

Location: src/metrics_tracker.py  AND  src/semantic_cache.py  (identical in both)

def get_redis_client():
    REDIS_SSL = os.getenv("REDIS_SSL", "true").lower() == "true"
    kwargs = {
        "host":                    os.getenv("REDIS_HOST"),
        "port":                    int(os.getenv("REDIS_PORT", 6380)),
        "password":                os.getenv("REDIS_PASSWORD"),
        "decode_responses":        True,
        "socket_timeout":          int(os.getenv("REDIS_SOCKET_TIMEOUT", 30)),
        "socket_connect_timeout":  int(os.getenv("REDIS_SOCKET_CONNECT_TIMEOUT", 30)),
    }
    if REDIS_SSL:
        kwargs["ssl"]           = True
        kwargs["ssl_cert_reqs"] = None   # <<< MUST be Python None — NOT string "none"
    return redis.Redis(**kwargs)

NUANCE 1 — ssl_cert_reqs must be Python None
  Wrong:  kwargs["ssl_cert_reqs"] = "none"    → causes auth failure / SSL handshake error
  Right:  kwargs["ssl_cert_reqs"] = None      → disables cert validation (Azure uses self-signed)

NUANCE 2 — No username parameter
  Newer versions of redis-py automatically send username="default"
  Azure Cache for Redis rejects any username parameter → "invalid username-password pair"
  Solution: ensure username is NOT in kwargs dict at all

NUANCE 3 — Port 6380 only
  Port 6379 (non-SSL) is disabled on Azure Redis by default
  Always use 6380

NUANCE 4 — REDIS_SSL env var is a string
  os.getenv("REDIS_SSL") returns the string "true" not Python True
  Must evaluate: .lower() == "true"

7. AUTH SYSTEM
================================================================================

Infrastructure layer: Azure SWA handles Microsoft AAD authentication.
All routes in staticwebapp.config.json require "authenticated" role.
Unauthenticated requests → SWA redirects to /.auth/login/aad automatically.

AuthGate.js flow on mount:
  1. GET /.auth/me
     → returns {clientPrincipal: {userId, identityProvider, userDetails, claims}}
     → null clientPrincipal = not authenticated (dev mode)

  2. Extract email from claims array — checked in this order:
     "emails"
     "email"
     "preferred_username"
     "http://schemas.xmlsoap.org/ws/2005/05/identity/claims/emailaddress"

  3. Extract name from claims array — checked in order:
     "name"
     "http://schemas.xmlsoap.org/ws/2005/05/identity/claims/name"

  4. GET /auth/validate/{userId}
     → {status: "unregistered"|"pending"|"approved"|"revoked", profile: {...}|null}

  5. Route based on status:
     approved     → render <App /> tabs
     pending      → "Access Pending Approval" holding screen
     revoked      → "Access Revoked" holding screen
     unregistered → registration form (full_name, email, title, company, country)

Registration:
  POST /register
  tristan.gitman@un.org → auto-approved immediately
  All other emails → status = "pending" → admin must approve

Admin approval:
  POST /auth/approve?user_id=X&approved_by=Y
  POST /auth/revoke?user_id=X&revoked_by=Y
  Both available in Admin tab (visible only to tristan.gitman@un.org)

Dev mode (localhost):
  /.auth/me returns {"clientPrincipal": null}
  AuthGate sets devUser = {id: "dev_user", name: "Dev User", email: "", provider: "dev"}
  Dev user has empty email → isAdmin = false
  To test admin locally: manually set dev_user profile status to "approved" in Redis
    redis-cli -h governance-redis... -p 6380 -a PASSWORD --tls
    SET user:dev_user:profile '{"status":"approved","email":"tristan.gitman@un.org",...}'

Sign out:
  localhost  → POST /auth/logout-dev  (deletes Redis profile) + window.location.reload()
  production → window.location.href = "/.auth/logout"

isAdmin check (App.js):
  const isAdmin =
    profile?.email?.toLowerCase() === "tristan.gitman@un.org" ||
    user?.email?.toLowerCase() === "tristan.gitman@un.org";

9. REDIS KEY SCHEMA
================================================================================

User data:
  user:{user_id}:profile          → JSON string (full profile object)
  users:all                       → SET  all registered user_ids
  users:approved                  → SET  approved user_ids
  users:pending                   → SET  pending user_ids
  users:revoked                   → SET  revoked user_ids

Profile JSON structure:
  {
    user_id, provider, full_name, email, title, company, country,
    registered_at (ISO), last_active (ISO), status,
    approved_by (optional), approved_at (optional),
    revoked_by (optional), revoked_at (optional)
  }

Rate limiting:
  user:{user_id}:requests         → counter with TTL=60s (10 req/min enforcement)

Per-user metrics:
  user:{user_id}:total_queries    → integer counter
  user:{user_id}:style:{style}    → counter per style
  user:{user_id}:hallucinations   → integer counter
  user:{user_id}:latencies        → LIST of floats (last 100, LPUSH+LTRIM)
  user:{user_id}:last_active      → ISO timestamp string

Global metrics:
  metrics:total_queries           → integer counter (INCR)
  metrics:cache_hits              → integer counter
  metrics:hallucinations          → integer counter
  metrics:pii_detected            → integer counter
  metrics:style:{style}           → counter per style (factual/analytical/summary/safety/adversarial)
  metrics:source:{source}         → counter per document source
  metrics:latencies               → LIST of floats (last 1000, LPUSH+LTRIM)
  metrics:feedback:positive       → integer counter
  metrics:feedback:negative       → integer counter

Security:
  security:injection              → integer counter
  security:pii                    → integer counter
  security:rate_limit             → integer counter

Semantic cache:
  cache:{hash}                    → JSON string with TTL=3600s
  Hash = hash(query + prompt_type + topic)
  JSON: {query, answer, prompt_type, topic, vector: [1536 floats]}

Feedback:
  feedback:all                    → SET of query_ids
  feedback:{query_id}             → JSON string (full feedback record)
  feedback:positive               → SET of positive query_ids
  feedback:negative               → SET of negative query_ids

18. QUERY PIPELINE
================================================================================

POST /query execution order (src/api.py):

1. classify_query(question)
   Single LLM call (gpt-4o-mini) returns:
     is_meta      bool   Is this a question about the system itself?
     is_injection bool   Does this look like a prompt injection attempt?
     style        str    factual / analytical / summary / safety / adversarial
     topic        str    Detected topic

2. If is_meta → answer_meta_question(question) using SYSTEM_CONTEXT string
   Return immediately — no RAG, no Elasticsearch call

3. run_security_checks(question, user_id, is_injection)
   a. Azure Language PII detection on raw question
   b. Rate limit check (Redis counter — 10 req/60s per user_id)
   c. Injection flag from step 1 classifier
   If any check fails → raise HTTPException 400 + increment security counter
   Response body includes human-readable message (not raw JSON)

4. anonymize_pii(question)
   Azure Language replaces PII entities with [ENTITY_TYPE] tags
   Returns clean_query (safe to send to LLM)

5. build_chain(prompt_type=style, topic=topic)
   Selects matching template from prompt_library.py (5 templates)
   Constructs LangChain pipeline:
     semantic_cache_check → elasticsearch_retrieve → llm_call

6. chain.invoke(clean_query)
   a. Check Redis semantic cache (0.95 cosine threshold)
      Cache hit → return cached answer immediately
   b. Elasticsearch hybrid search (BM25 + kNN, top_k=5)
   c. Format context from retrieved chunks with source citations
   d. Call fine-tuned GPT-4o-mini with prompt template
   Returns {answer, context, sources, cache_hit}

7. detect_hallucination(question, answer, context)
   GPT-4o-mini judge evaluates whether answer is grounded in context
   Returns {is_hallucination, confidence, reason}
   High confidence + is_hallucination → increment metrics:hallucinations

8. Track metrics (non-fatal — wrapped in try/except)
   Increment: total_queries, style counter, source counter
   Append to latencies list
   Track LangSmith run via callbacks
   Update user-specific metrics

9. Return QueryResponse
   {answer, hallucination_score, is_hallucination, detected_style,
    sources, cache_hit, latency_ms, pii_detected}
